# Data Models

- Status: `Active`
- Related ADRs: `ADR-004` (PostgreSQL), `ADR-005` (Redis)
- Owner: `Engineering Lead`

## 1. Purpose

Define the data the system owns: the domain types the code speaks in, the PostgreSQL schema
that persists them, the in-memory equivalent used in tests, and the optional ephemeral store.
This is the schema of record for the `auth_*` tables, `content_items`,
`scholar_verifications`, `community_threads`, `community_replies`, `community_reports`, and
`saved_items`, and the contract every repository implementation must satisfy.

## 2. Domain Types

Identity types are defined in `src/modules/identity/domain/auth-types.ts` (§2.1–§2.5),
content types in `src/modules/content/domain/content-types.ts` (§2.6), verification types
in `src/modules/verification/domain/verification-types.ts` (§2.7), community types in
`src/modules/community/domain/community-types.ts` (§2.8), and library types in
`src/modules/library/domain/library-types.ts` (§2.11). Types are the shared language;
storage is an implementation detail behind each module's repository interface
(`AuthRepository`, `ContentRepository`, `VerificationRepository`, `CommunityRepository`,
`LibraryRepository`).

### 2.1 `UserProfile`

The publicly safe view of a user (no secrets).

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | UUID, primary key |
| `phoneNumber` | `string` | Normalized `+880…`, unique |
| `email` | `string`, optional | Secondary recovery contact (password reset); **not unique**, never in `PublicProfile` |
| `displayName` | `string` | 2–80 chars |
| `locale` | `string` | Defaults to `bn-BD` |
| `roles` | `("learner" \| "scholar" \| "admin")[]` | Defaults to `["learner"]` |
| `createdAt` | `string` (ISO) | |
| `updatedAt` | `string` (ISO) | |
| `lastLoginAt` | `string` (ISO), optional | Set on session creation |
| `passwordUpdatedAt` | `string` (ISO) | Set on register and password reset |

The profile read surface exports `PublicProfile = { id, displayName, roles, createdAt }` (via
`getPublicProfile` in `auth-service.ts`): the identity fields a member profile may show. It
never carries `phoneNumber`, `email`, `passwordHash`, or `passwordUpdatedAt`, so a profile page
cannot leak a member's contact details (see [member-profile-slice.md](member-profile-slice.md) §7,
[password-reset-delivery-slice.md](password-reset-delivery-slice.md) §5). The `email` is captured
optionally at registration and is editable by its owner through `PATCH /api/auth/profile`
(§3.1, §6).

### 2.2 `UserRecord = UserProfile & { passwordHash: string }`

The stored form. `passwordHash` never leaves the application layer — `sanitizeUser()`
strips it before any value is returned to a route or a client.

### 2.4 `PasswordResetRecord`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | UUID |
| `userId` | `string` | FK → `auth_users.id` |
| `tokenHash` | `string` | SHA-256 of the reset code, unique |
| `createdAt` | `string` (ISO) | |
| `expiresAt` | `string` (ISO) | |
| `usedAt` | `string` (ISO), optional | Set on successful confirm |

The record shape is unchanged by the password-reset-delivery slice: `tokenHash` is still the
SHA-256 hash of the token, but the plaintext that is hashed is now the **6-digit numeric reset
code** (not a 48-character hex string), so it is typeable on a phone
([password-reset-delivery-slice.md](password-reset-delivery-slice.md) §5, §9). The record stays
single-use (`usedAt`) and time-boxed (`PASSWORD_RESET_MAX_AGE_SECONDS`).

### 2.5 Token claim types

`AccessTokenClaims` (`sub`, `sessionId`, `phoneNumber`, `roles`, `type: "access"`) and
`RefreshTokenClaims` (`sub`, `sessionId`, `type: "refresh"`) describe the JWT payloads. The
raw token values are only ever held in memory or in httpOnly cookies — persisted state keeps
the SHA-256 *hash* of the refresh token, and reset tokens are likewise only stored hashed.

### 2.6 `ResearchItem` (content)

The published research-comprehension unit. Defined in
`src/modules/content/domain/content-types.ts`.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | UUID, primary key, used as the `/content/[id]` path segment |
| `title` | `string` | Source-language title |
| `abstract` | `string` | Source-language abstract |
| `summaryBn` | `string` | Bangla comprehension summary (the product value). Optional to save (a draft stores `""`); required to publish, and generated by the AI when blank (see §2.10, `ai-summarization-slice.md`) |
| `sourceLanguage` | `string` | Abstract language, defaults to `en` |
| `tags` | `string[]` | Stored as `jsonb` |
| `status` | `"draft" \| "published"` | Only `published` items are listable/readable |
| `sourceUrl` | `string`, optional | External source link |
| `publishedAt` | `string` (ISO), optional | Keyset-pagination sort key |
| `authorId` | `string`, optional | Set on create; the authoring user (see `content-authoring-slice.md`) |
| `updatedBy` | `string`, optional | Set on create and every update |
| `createdAt` | `string` (ISO) | |
| `updatedAt` | `string` (ISO) | Doubles as the optimistic-concurrency token |

Related types: `ResearchItemStatus`, `ContentAuthor` (`{ id, roles }`), `CreateItemInput`,
`UpdateItemInput` (adds the optional `updatedAt` concurrency token), and `ContentRepository`
(`listPublishedItems`, `listItems`, `getPublishedItemById`, `getPublishedItemsByIds`,
`listPublishedItemsByAuthor`, `listDistinctPublishedTags`, `listPublishedItemsByTag`,
`getItemById`, `createItem`, `updateItemIfUnchanged`).
`listPublishedItems`/`getPublishedItemById`/`getPublishedItemsByIds` are the public read path
(published only); `listPublishedItemsByAuthor` is the profile read (one author's published
items, `publishedAt` descending); `listDistinctPublishedTags` and `listPublishedItemsByTag`
are the browse reads (see `topic-browse-slice.md`) — the former returns published
counts keyed by tag (`TagCount = { tag, count }`, count descending then tag ascending), the
latter returns one exact tag's published items `publishedAt` descending, capped by `limit`;
`listItems`/`getItemById` are the authoring path and return drafts too. Pagination types:
`ContentCursor = { publishedAt, id }`, `ListPublishedItemsOptions`, `ListPublishedItemsResult`,
`ListItemsByAuthorOptions` (`{ limit }`), and `ListPublishedItemsByTagOptions` (`{ limit }`).

| `reporterId` | `string` | The reporting member, stamped from the session; admin-only on reads |
| `targetType` | `"thread" \| "reply"` | What is being reported |
| `targetId` | `string` | The reported thread or reply id |
| `reason` | `ReportReason` | `spam \| harassment \| misinformation \| off-topic \| other` |

Related types: `ModerationState = "visible" | "hidden"`, `ModerationAction = "hide" | "restore" |
"lock" | "unlock"`, `ModerateThreadInput`, `ModerateReplyInput`, `CommunityThreadSummary`
(`CommunityThread & { replyCount }`, derived on the list read), `CommunityThreadDetail`
(`{ thread, replies }`), `CommunityActor` (`{ id, roles }`), `CreateThreadInput`,
`CreateReplyInput`, `CommunityCursor = { createdAt, id }`, `ListThreadsOptions`,
`ListThreadsByCategoryOptions` (`{ limit?; cursor? }`), `TagCount`-style `CategoryCount`
(`{ category, count }`), `ListRepliesOptions`, `ListThreadsResult`,
`ReportTargetType = "thread" | "reply"`, `ReportStatus = "open" | "resolved" | "dismissed"`,
`ReportReason = "spam" | "harassment" | "misinformation" | "off-topic" | "other"`,
`CreateReportInput` (`{ targetType, targetId, reason, detail? }`),
`ResolveReportInput` (`{ action: "resolve" | "dismiss"; note? }`),
`ReportQueueEntry` (`{ report, thread, reply? }`, the joined triage read),
`ListReportsOptions` (`{ status?; limit }`), and `CommunityRepository`
(`listThreads`, `listThreadsByAuthor`, `listDistinctCategories`, `listThreadsByCategory`,
`getThreadById`, `createThread`, `listRepliesByThreadId`, `createReply`,
`getReplyById`, `updateThreadModeration`, `updateReplyModeration`,
`createReport`, `getReportById`, `listReports`, `updateReport`).
`createReport` is **idempotent per member and item** — the unique triple
`(reporterId, targetType, targetId)` means a second report by the same member on the same item
returns the pre-existing report rather than creating a duplicate (`member-reporting-slice.md` §5).
`listReports` filters by `status` (the queue passes `open`) and orders by `createdAt`/`id`
descending. The report is deliberately **decoupled from visibility**: filing one never changes
the target's `moderationState`; only an explicit hide/restore moderation action does
(`member-reporting-slice.md` §7).
`listThreadsByAuthor` is the profile read (one author's threads, `createdAt` descending) and is
always visible-only. `listDistinctCategories` and `listThreadsByCategory` are the browse reads
(see `topic-browse-slice.md`): the former returns visible-thread counts keyed by category
(`CategoryCount = { category, count }`, count descending then category ascending), the latter
returns one category's visible threads `createdAt` descending with keyset pagination — **both
are always visible-only**, so a hidden thread can never leak through a category count or list.
`replyCount` is derived, never stored — a correlated subquery in PostgreSQL, a scan over the
replies map in memory.
**Moderation visibility is a repository rule** (`community-moderation-slice.md` §5):
`listThreads`/`listRepliesByThreadId` take an `includeHidden?` flag that only the moderator
surfaces pass, so the member list, the thread detail, the profile list, and the derived
`replyCount` all omit hidden rows from one place. `getThreadById` returns a row in **any** state;
the service decides whether the caller may see it.

### 2.9 Search read model (search)

The discovery read model. These types are **derived** — nothing here is persisted; `search`
projects published research and community threads into a flat list at read time. Defined in
`src/modules/search/domain/search-types.ts`.

`SearchKind` = `"research" | "thread"`; `SearchSort` = `"relevance" | "newest"`.

`SearchDocument` (a projection of one `ResearchItem` or `CommunityThread`):

| Field | Type | Notes |
| --- | --- | --- |
| `kind` | `SearchKind` | Which source produced the row |
| `id` | `string` | Source row id |
| `title` | `string` | Scored field |
| `body` | `string` | Research: `abstract + summaryBn`; thread: `body`. Scored field |
| `tags` | `string[]` | Research tags, or the thread category. Scored field |
| `authorId` | `string?` | For the author filter |
| `createdAt` | `string` (ISO) | Sort key |

`SearchQuery` — what the repository receives: `{ tokens, kind?, tags?, category?, authorId?,
limit }`. `tokens` are lower-cased query words; the repository requires **every** token to
appear (AND), case-insensitively, in the title, body, or tag text.

`SearchCriteria` — the normalized query the service works with: `{ query, kind?, tag?,
category?, author?, sort, limit }`.

`SearchHit` — a scored `SearchDocument`: `{ kind, id, title, excerpt, tags, authorId?,
createdAt, href, score }`. `excerpt` is the body trimmed to 180 chars with a `…` suffix;
`href` is `/content/[id]` for research and `/community/[id]` for threads.

`SearchResult` = `{ hits: SearchHit[]; total: number }` — `hits` is the paginated slice,
`total` is the count before slicing.

`SearchRepository` = `{ searchDocuments(query: SearchQuery): Promise<SearchDocument[]> }`. The
in-memory implementation composes the content and community memory stores; the PostgreSQL
implementation runs an `ILIKE`-per-token query over `content_items` (`status = 'published'`)
and `community_threads`.

### 2.10 Summarization types (summarization)

The AI summarization contract. These types are **derived** — the English summary is never
persisted and the module has no store. Defined in
`src/modules/summarization/domain/summarization-types.ts`.

`SummarizeInput` = `{ title, abstract, sourceLanguage }` — the plain input a provider receives.
The module never imports the content module; the composition root passes these fields.

`SummaryResult` = `{ summaryEn, summaryBn }` — both non-empty (≤ 5000 chars). Only `summaryBn`
is persisted (into the item's `summaryBn`); `summaryEn` is a transient preview returned in the
publish response.

`SummaryProvider` = `{ summarize(input: SummarizeInput): Promise<SummaryResult> }` — implemented
by the deterministic fake provider (test) and the Gemini provider.

### 2.11 `SavedItem` (library)

The per-member save relation — a member's saved research item. Defined in
`src/modules/library/domain/library-types.ts`.

| Field | Type | Notes |
| --- | --- | --- |
| `userId` | `string` | The acting member; the save is scoped to this id |
| `itemId` | `string` | The saved research item; the `(userId, itemId)` pair is the identity, so a save carries **no** surrogate id |
| `savedAt` | `string` (ISO) | The list sort key (descending) |

Related types: `LibraryActor` (`{ id, roles }`, resolved from identity at the composition
root), `SaveItemInput` (`{ itemId }`), `ListSavedItemsInput` (`{ limit? }`),
`ListSavedItemsOptions` (`{ limit }`), `LibraryStore` (`{ saves: Map<string, SavedItem> }`,
keyed `${userId}:${itemId}`), and `LibraryRepository` (`listSavedItems`, `isItemSaved`,
`saveItem`, `removeSavedItem`, `countSavedItems`). `saveItem` is an idempotent upsert on
`(userId, itemId)`: it returns the save that is stored afterwards (the new one, or the
pre-existing save); `countSavedItems` is the profile rollup (the exact number the member has
saved). The module
stores **no item content** — it imports content **types only** where it must name an item;
hydration and the published-item check happen at the composition root (§8 of
[library-slice.md](library-slice.md)).

### 2.12 Notification types (platform)

The cross-cutting notification contract — the port `identity` delivers password-reset codes
through. These types are **derived** — the module has no store. Defined in
`src/modules/platform/domain/notification-types.ts`.

`NotificationDestination` = `{ phoneNumber: string; email?: string }` — the recipient's contact
points.

`NotificationMessage` = `{ destination; subject; body }` — the plain message a channel sends.

`NotificationChannel` = `{ kind: "sms" | "email" | "log"; send(message: NotificationMessage):
Promise<void> }` — a channel skips itself when its required contact point is missing (the email
channel needs `destination.email`). The port is deliberately identity-agnostic (it carries only
contact points and text), so it can serve a future verification or moderation notification without
a new abstraction ([module-boundaries.md](module-boundaries.md) §5.2).

### 2.13 `Notification` (notifications)

The member inbox entry — an outcome a producer recorded for a member. Defined in
`src/modules/notifications/domain/notification-types.ts`.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | Surrogate id (uuid), generated by the service |
| `recipientId` | `string` | The notified member; the inbox is scoped to this id |
| `type` | `"content_hidden" \| "report_resolved" \| "report_dismissed"` | The outcome; each value has exactly one producer |
| `title` | `string` | Producer-written headline |
| `body` | `string` | Producer-written outcome text; never the moderation note, the moderator's identity, or the report's detail |
| `href` | `string` | The in-app link the inbox entry points at |
| `dedupeKey` | `string` | The item this entry is about; `(recipientId, dedupeKey)` is the idempotency identity |

Related types: `NotificationActor` (`{ id }`, resolved from identity at the composition root),
`CreateNotificationInput` (`{ recipientId, type, title, body, href, dedupeKey, destination? }` —
`destination` is **delivery-only** and never persisted), `ListNotificationsInput` (`{ limit? }`),
`ListNotificationsOptions` (`{ limit }`), `CreateNotificationResult`
(`{ notification, created }`), `NotificationStore`
(`{ notifications: Map<string, Notification> }`), and `NotificationRepository`
(`createNotification`, `listNotifications`, `getNotificationById`, `markNotificationRead`,
`markAllNotificationsRead`). `createNotification` is an idempotent insert on
`(recipientId, dedupeKey)`: it returns the entry that is stored afterwards (the new one, or the
pre-existing one) and whether this call created it; delivery happens **only** for a created entry.
The entry stores **no contact point** — the destination is resolved through identity at the
composition root and passed as delivery-only data
([notifications-slice.md](notifications-slice.md) §5, §7).

Timestamps are stored as ISO-8601
`text` (not `timestamptz`) because the domain deals in ISO strings and SQLite-free
portability is preferred over database-side timezone arithmetic; `roles`, `tags`, `degrees`,
`affiliations`, `specializations`, and `languages` are `jsonb`.

the tag search (`WHERE status = 'published' AND tags @> $1::jsonb ORDER BY published_at DESC,
id DESC LIMIT $2`) and the distinct-tag rollup
(`FROM content_items, jsonb_array_elements_text(tags) AS tag WHERE status = 'published' GROUP BY
tag ORDER BY count DESC, tag ASC`). Both come from
`migrations/20261128170000_add_topic_browse_indexes.cjs` (see `topic-browse-slice.md`).

| --- | --- | --- |

Composite primary key `(user_id, item_id)` — the pair is the identity of a save, so a duplicate

the item's existence and published status are checked at save time by the composition root
(see `library-slice.md` §7). The save is an idempotent upsert
(`INSERT … ON CONFLICT (user_id, item_id) DO NOTHING`), and removal is a plain
`DELETE … WHERE user_id = $1 AND item_id = $2` whose affected-row count is the result.

### 3.9 `community_reports`

The member-filed report about a thread or reply, and its moderator triage state. Created by
`migrations/20261128190000_create_community_reports.cjs` (`member-reporting-slice.md` §9).

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `text` | primary key |
| `reporter_id` | `text` | not null |
| `target_type` | `text` | not null (`thread` \| `reply`) |
| `target_id` | `text` | not null |
| `reason` | `text` | not null |
| `detail` | `text` | nullable |
| `status` | `text` | not null, default `open` (`open` \| `resolved` \| `dismissed`) |
| `created_at` | `text` | not null |
| `resolved_by` | `text` | nullable |
| `resolved_at` | `text` | nullable |
| `resolution_note` | `text` | nullable |

Index `community_reports_reporter_target_uidx` — **unique** on
`(reporter_id, target_type, target_id)`: the idempotency guarantee (one report per member per
item), so a repeat report is a no-op at the database, not only in the service
(`member-reporting-slice.md` §7, §9). Index `community_reports_status_created_at_idx` on
`(status, created_at, id)` to support the queue read
(`WHERE status = $1 ORDER BY created_at DESC, id DESC LIMIT $2`, satisfied by a backward index
scan then a limit). There is **no cross-table foreign key**: `reporter_id`, `target_id`, and
`resolved_by` store bare ids as `text` (matching `author_id`/`moderated_by`), and `target_id`
is polymorphic, so it cannot carry a single FK. The file is a brand-new table, so the migration
rewrites no existing row and adds no locks beyond the `create table`.

The write is an **idempotent insert**
(`INSERT … ON CONFLICT (reporter_id, target_type, target_id) DO NOTHING`, then a select-back by
the same triple), so the reporter always receives the stored report whether it was just created
or already existed. Triage is a plain
`UPDATE … SET status = $1, resolved_by = $2, resolved_at = $3, resolution_note = $4 WHERE id = $5`.
Writing a report **never touches** `community_threads.moderation_state` /
`community_replies.moderation_state` — filing never auto-hides; only an explicit hide/restore
moderation action changes visibility (`member-reporting-slice.md` §7).

### 3.10 `notifications`

The member inbox entry recorded by a producer (a hidden item's author, or a closed report's
reporter). Created by `migrations/20261128200000_create_notifications.cjs`
(`notifications-slice.md` §9.1).

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `text` | primary key |
| `recipient_id` | `text` | not null |
| `type` | `text` | not null (`content_hidden` \| `report_resolved` \| `report_dismissed`) |
| `title` | `text` | not null |
| `body` | `text` | not null |
| `href` | `text` | not null |
| `dedupe_key` | `text` | not null |
| `read_at` | `text` | nullable (set when the member marks it read) |
| `created_at` | `text` | not null |

Index `notifications_recipient_dedupe_uidx` — **unique** on `(recipient_id, dedupe_key)`: the
idempotency guarantee (one notification per member per item), so a repeated moderation call — or a
re-hide after a restore — is a no-op at the database, not only in the service
(`notifications-slice.md` §7, §9). Index `notifications_recipient_created_at_idx` on
`(recipient_id, created_at, id)` to support the newest-first inbox read
(`WHERE recipient_id = $1 ORDER BY created_at DESC, id DESC LIMIT $2`). There is **no cross-table
foreign key**: `recipient_id` stores a bare id as `text` (matching `author_id`/`reporter_id`).
The write is an **idempotent insert**
(`INSERT … ON CONFLICT (recipient_id, dedupe_key) DO NOTHING RETURNING …`, then a select-back by
the pair), so the service always learns the stored row and whether it was new (delivery happens
only when it was). Mark-read is `UPDATE … SET read_at = $1 WHERE id = $2 AND read_at IS NULL`;
mark-all-read is `UPDATE … WHERE recipient_id = $2 AND read_at IS NULL`, returning the affected
count. The file is a brand-new table, so the migration rewrites no existing row.

### 3.11 Migration Operations

Managed by `node-pg-migrate` (config keys kebab-case, `single-transaction: true`). See
`docs/configuration.md` for commands. The auth migration's `down` drops the three tables in
dependent order (`auth_password_resets`, then the index, then `auth_sessions`, then
`auth_users`); the content migration's `down` drops the index, then `content_items`; the
authorship migration's `down` drops `author_id` and `updated_by`; the verification migration's
`down` drops both indexes, then `scholar_verifications`; the community migration's `down` drops
both indexes, then `community_replies`, then `community_threads`; the library migration's
`down` drops the index, then `saved_items`; the member-profile migration's `down` drops the two
author indexes (`community_threads_author_id_created_at_idx` then
`content_items_author_id_published_at_idx`) and touches no table; the community-moderation
migration's `down` drops the reply moderation columns before the thread moderation columns;
the topic-browse migration's `down` drops both browse indexes
(`community_threads_category_created_at_idx` then `content_items_tags_gin_idx`) and touches no
table; the email migration's `down` drops the `email` column from `auth_users` and touches no
other column; the community-reports migration's `down` drops `community_reports` (and with
it both of its indexes) and touches no other table; and the notifications migration's `down`
drops `notifications` (and with it both of its indexes) and touches no other table.

## 4. In-Memory Store

### 4.1 Identity store

Defined in `src/modules/identity/infrastructure/auth-store.ts`. `AuthStore` mirrors the
schema with four `Map`s:

| Map | Key → Value |
| --- | --- |
| `usersById` | `id` → `UserRecord` |
| `usersByPhone` | `phoneNumber` → `id` (the unique index) |
| `sessionsById` | `id` → `AuthSessionRecord` |
| `passwordResetById` | `id` → `PasswordResetRecord` |

`listSessionsByUserId` and `getPasswordResetByTokenHash` are linear scans over the maps,
which is correct at test scale. The store is cached on `globalThis` so hot reloads do not
lose data, and `resetAuthStoreForTesting()` replaces it between tests.

### 4.2 Content store

Defined in `src/modules/content/infrastructure/content-store.ts`. `ContentStore` holds a
single `items: Map<string, ResearchItem>` keyed by `id`. `listPublishedItems` filters to
`status === "published"`, sorts by `publishedAt`/`id` descending, applies the keyset cursor,
and slices to the requested limit; `getPublishedItemById` returns `undefined` for drafts or
unknown ids; `listPublishedItemsByAuthor` filters to one author's published items sorted by
`publishedAt`/`id` descending and truncates to the limit; `listDistinctPublishedTags` scans the
items, counts published items per tag, and returns `TagCount`s sorted by count descending then
tag ascending; `listPublishedItemsByTag` filters to published items carrying the exact tag,
sorted by `publishedAt`/`id` descending and truncated to the limit. The authoring methods
mirror the read path: `listItems` returns every status
sorted by `updatedAt`/`id` descending, `getItemById` returns drafts too, and
`updateItemIfUnchanged` writes only when the stored `updatedAt` matches the expected value
(returning `false` otherwise, which the service turns into a `409`). Like the identity store
it is cached on `globalThis` (`__okkhorContentStore`) and replaced between tests by
`resetContentStoreForTesting()`.

### 4.3 Verification store

Defined in `src/modules/verification/infrastructure/verification-store.ts`.
`VerificationStore` holds a single `verifications: Map<string, ScholarVerification>` keyed by
`id`. `getByApplicantId` is a linear scan (correct at test scale), `listByStatus` filters by
`status` and sorts by `updatedAt`/`id` descending, and `updateIfUnchanged` writes only when the
stored `updatedAt` matches the expected value (returning `false` otherwise, which the service
turns into a `409`). Like the other stores it is cached on `globalThis`
(`__okkhorVerificationStore`) and replaced between tests by `resetVerificationStoreForTesting()`.

### 4.4 Community store

Defined in `src/modules/community/infrastructure/community-store.ts`. `CommunityStore` holds
three `Map`s keyed by `id`: `threads: Map<string, CommunityThread>`,
`replies: Map<string, CommunityReply>`, and `reports: Map<string, CommunityReport>`. `listThreads` filters to visible threads unless
`includeHidden`, sorts by `createdAt`/`id` descending, applies the keyset cursor, derives
`replyCount` by scanning the replies map, and slices to the requested limit (returning a
`nextCursor` while a further page remains). `listRepliesByThreadId` filters by `threadId` and
sorts ascending, omitting hidden replies unless `includeHidden`; `listThreadsByAuthor` filters
to one author's **visible** threads sorted by `createdAt`/`id` descending and derives
`replyCount` for each; `listDistinctCategories` counts **visible** threads per category and
returns `CategoryCount`s sorted by count descending then category ascending;
`listThreadsByCategory` returns one category's **visible** threads sorted by `createdAt`/`id`
descending with the same keyset cursor and derived `replyCount`. `getReplyById` returns a reply
in any state; `updateThreadModeration` and
`updateReplyModeration` overwrite the stored row's moderation columns. The reporting methods
mirror the persistence path: `createReport` scans the `reports` map for a matching
`(reporterId, targetType, targetId)` and returns the existing report if found (the in-memory
form of the unique index), `getReportById` looks a report up by id, `listReports` filters by
`status` (the queue passes `open`) and sorts by `createdAt`/`id` descending before slicing to
the limit, and `updateReport` overwrites the stored row's triage columns. Like the other stores
it is cached on `globalThis`
(`__okkhorCommunityStore`) and replaced between tests by `resetCommunityStoreForTesting()`.

### 4.5 Search read model (no store)

`search` has no store of its own. Its in-memory repository
(`src/modules/search/infrastructure/search-store.ts`) is a stateless projection: on each
`searchDocuments` call it reads `getMemoryContentRepository().listItems()` and
`getMemoryCommunityRepository().listThreads(...)`, filters them, and returns `SearchDocument`s.
It is cached on `globalThis` (`__okkhorMemorySearchRepository`) but holds no data, so it needs
no reset hook — resetting the content and community stores is enough.

### 4.6 Library store

Defined in `src/modules/library/infrastructure/library-store.ts`. `LibraryStore` holds a single
`saves: Map<string, SavedItem>` keyed `${userId}:${itemId}` — the pair is the save's identity,
mirroring the composite primary key. `listSavedItems` filters to the member's saves, sorts by
`savedAt` descending then `itemId` descending, and truncates to the requested limit;
`isItemSaved` is a map lookup; `saveItem` is an idempotent upsert that returns the pre-existing
save when the pair is already present; `countSavedItems` counts the member's saves (the profile
rollup). Like the other stores it is cached on `globalThis`
(`__okkhorLibraryStore` / `__okkhorMemoryLibraryRepository`) and replaced between tests by
`resetLibraryStoreForTesting()`.

### 4.7 Notifications store

Defined in `src/modules/notifications/infrastructure/notification-store.ts`.
`NotificationStore` holds a single `notifications: Map<string, Notification>` keyed by `id`.
`createNotification` scans for a matching `(recipientId, dedupeKey)` and returns the existing entry
if found (the in-memory form of the unique index), otherwise inserts and reports `created: true`;
`listNotifications` filters to the member's entries, sorts by `createdAt` descending then `id`
descending, and truncates to the limit; `getNotificationById` is a map lookup;
`markNotificationRead` sets `read_at` on an unread entry (returning the existing one unchanged when
already read); `markAllNotificationsRead` sets `read_at` on every unread entry of the member and
returns the count. Like the other stores it is cached on `globalThis`
(`__okkhorNotificationStore` / `__okkhorMemoryNotificationRepository`) and replaced between tests
by `resetNotificationStoreForTesting()`.

## 5. Persistence Driver Selection

### 5.1 Auth repository

`src/modules/identity/infrastructure/auth-repository.ts` is the single decision point:

```
AUTH_STORAGE_DRIVER = auto | memory | postgres   (default: auto)
  memory   → memory repository
  postgres → postgres repository
  auto     → NODE_ENV === "test"        → memory
             else DATABASE_URL present  → postgres
             else                       → throw (misconfiguration)
```

Both implementations satisfy the `AuthRepository` interface (11 methods). Application code
never imports a concrete implementation — it calls `getAuthRepository()`.

### 5.2 Ephemeral store (rate-limit counters)

`src/modules/platform/infrastructure/ephemeral-store.ts` follows the same pattern for the
`ADR-005` boundary:

```
EPHEMERAL_STORAGE_DRIVER = auto | memory | redis   (default: auto)
  memory → in-process counters
  redis  → Redis INCR + EXPIRE
  auto   → NODE_ENV === "test"       → memory
           else REDIS_URL present    → redis
           else                      → memory
```

Unlike the auth repository, a missing Redis is **not** an error: the store is optional by
design, and losing it degrades behaviour (rate limits become per-instance and best-effort)
rather than losing durable data. The interface is intentionally tiny:
`increment(key, windowSeconds)`.

### 5.3 PostgreSQL connection

`src/modules/platform/infrastructure/postgres-config.ts` holds the shared pool config and
reads pool settings from the environment:
`DB_POOL_MAX` (default 10), `DB_POOL_IDLE_TIMEOUT_MS` (10 000),
`DB_POOL_CONNECTION_TIMEOUT_MS` (5 000), `DB_POOL_MAX_USES` (7 500), and
`allowExitOnIdle` in non-production.

```
  sms        → the SMS gateway channel
  email      → the email gateway channel
  sms+email  → both gateway channels
  auto       → NODE_ENV === "test"                     → [log]
               else every channel whose gateway URL is set → [sms?, email?]
               else NODE_ENV !== "production"           → [log]
               else                                     → []  (no channels)
```

The selector returns the resolved `NotificationChannel[]`; the identity use case
(`requestPasswordReset`) sends through all of them with per-channel failure isolation, and — since
the notifications slice — the `notifications` producers do the same through `createNotification`
(§2.13), resolving the recipient's contact points at the composition root via identity's
`getNotificationDestinationById`. Unlike the
storage drivers, the notification channels have **no repository and no store** — the `log` channel
records the last message on `globalThis` (with a `reset…ForTesting()` hook) purely so tests can
assert delivery without a network call. Each gateway channel POSTs a small JSON body with a bearer
header and aborts on its timeout (`NOTIFICATION_*_TIMEOUT_MS`), reading its credentials only in
`infrastructure` ([configuration.md](../configuration.md)).

## 6. Data Classification and Handling

| Data | Classification | Handling rule |
| --- | --- | --- |
| `password_hash` | secret | bcryptjs, 12 salt rounds; never returned |
| `refresh_token_hash` | secret-derived | SHA-256; raw token only in the cookie |
| `token_hash` (reset) | secret-derived | SHA-256 of the 6-digit code; the plaintext exists only in the delivery call (and the dev-only `log` preview) |
| `phone_number` | personal | Stored normalized; hashed before use in any rate-limit key |
| `email` | personal | Stored as-is; a secondary recovery contact, returned only to its owner, never in `PublicProfile` |
| Rate-limit identifiers | personal | SHA-256 before entering the keyspace |

Raw refresh/reset codes and passwords are never written to durable storage, logs, or response
bodies; the reset code is delivered out of band (SMS, and email when one is on file), and the
`resetTokenPreview` appears **only** under the dev/test `log` channel outside production
([password-reset-delivery-slice.md](password-reset-delivery-slice.md) §7).

## 7. Lifecycle and Retention

- **Sessions** expire after the refresh-token window (7 days) and are revoked on logout,
  rotation, or password reset. There is **no automatic pruning job yet** — expired session
  rows remain until a cleanup task exists.
- **Password resets** expire after 15 minutes and are single-use (`used_at`); no pruning job
  yet.
- **Rate-limit counters** are TTL-bound in Redis (or window-bound in memory) and need no
  pruning.

Automatic retention jobs are future work, not a current behaviour.

## 8. Adding a New Table

1. Add a migration under `migrations/` (kebab-case config, `single-transaction: true`),
   including a matching `down`.
2. Add or extend the domain types in the owning module's `domain/`.
3. Extend the `AuthRepository`-style interface and **both** implementations (memory +
   postgres).
4. Add a unit test for the memory path and an integration test against PostgreSQL.
5. Update this document's schema tables and classification table.
